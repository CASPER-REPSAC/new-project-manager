# AI 활용 개발용 WBS

## 0. 문서 목적

이 문서는 Notion + Outline + PDF Showcase 성격의 지식 관리/프로젝트 매니저 제품을 4인 개발팀과 AI 코딩 도구(Codex, Claude 등)로 구현하기 위한 작업 분해 구조(WBS)이다.

핵심 운영 원칙은 **도메인별 풀스택(Vertical Slice)** 개발이다. 프론트엔드와 백엔드를 인위적으로 분리하지 않고, 각 담당자가 자신의 도메인 기능을 UI, API, DB, 테스트까지 끝까지 책임진다.

## 1. AI 개발 운영 원칙

### 1.1 AI 에이전트 사용 기준

- **Codex**: 저장소 분석, 구현, 리팩터링, 테스트 작성, 버그 수정, CI 실패 원인 분석에 사용한다.
- **Claude**: 요구사항 해석, 설계 검토, UX 플로우 점검, 복잡한 도메인 로직 설명, 문서 초안 작성에 사용한다.
- **공통 원칙**: AI에게 작업을 맡길 때는 WBS ID, 관련 FR, 기대 산출물, 수정 범위, 검증 명령을 함께 제공한다.
- **금지 원칙**: 에디터 코어, CRDT, PDF 렌더링, 전문 검색 엔진처럼 검증된 오픈소스가 있는 영역을 처음부터 직접 구현하지 않는다.

### 1.2 AI 작업 요청 템플릿

```md
작업 ID: WBS-<ID>
목표: <구현/수정 목표>
관련 요구사항: FR-<번호>
수정 범위: <파일/모듈/도메인>
기술 제약: <사용 라이브러리, 금지 사항, 성능 조건>
완료 기준:
- <동작 기준>
- <테스트 기준>
- <문서/타입/마이그레이션 기준>
검증 명령:
- <lint/typecheck/test/build 명령>
```

### 1.3 개발 완료 기준

각 WBS 항목은 다음 조건을 만족해야 완료로 본다.

- 기능 요구사항이 UI, API, DB, 권한, 에러 처리까지 연결되어 있다.
- 핵심 경로에 대한 단위 테스트 또는 E2E 테스트가 존재한다.
- 타입, 린트, 빌드, 마이그레이션 검증이 통과한다.
- 사용한 오픈소스 라이브러리의 래핑 경계와 커스텀 확장 지점이 문서화되어 있다.
- AI가 생성한 코드는 담당 개발자가 리뷰하고 불필요한 추상화, 중복, 미사용 코드를 제거한다.

## 10. 4인 팀의 3대 가속화 개발 규칙

### 10.1 오픈소스 코어를 연결하고 확장한다

복잡도가 높은 에디터 코어(TipTap/Lexical), 실시간 동시 편집 엔진(Yjs), PDF 뷰어(Pdf.js), 전문 검색 엔진(Meilisearch)은 직접 구현하지 않는다. 팀의 역량은 검증된 엔진을 제품 요구사항에 맞게 커스텀 플러그인과 비즈니스 로직 래퍼로 연결하는 데 집중한다.

### 10.2 컴포넌트 중심 개발과 디자인 시스템 재사용을 우선한다

프로젝트 카드, 캘린더, 칸반 보드, 테이블 등 레이아웃 공수가 큰 UI는 기본 HTML/CSS부터 작성하지 않는다. Radix UI, Tailwind UI, Ag-Grid 등 검증된 UI 컴포넌트를 래핑하고, Dev 3이 공통 디자인 시스템과 상태 관리 규칙을 관리한다.

### 10.3 선언적 스키마와 코드 생성을 표준화한다

ORM 스키마와 API 명세(OpenAPI/GraphQL Schema)를 단일 진실 공급원(SSOT)으로 삼는다. 스키마 변경 시 TypeScript 타입, DB 마이그레이션, API 클라이언트 코드가 자동 생성되도록 하여 팀원 간 인터페이스 불일치와 반복 수작업을 줄인다.

## 13. 우선순위 기준

1. 인증, 워크스페이스, 문서 트리, 에디터 코어처럼 다른 기능의 기반이 되는 작업을 먼저 끝낸다.
2. 에디터, 데이터베이스, PDF 뷰어는 각각 작은 수직 슬라이스로 먼저 동작하게 만든 뒤 고급 기능을 확장한다.
3. 실시간 협업, 권한, 검색, Import/Export는 데이터 무결성과 보안 영향이 크므로 테스트 없이 병합하지 않는다.
4. AI가 작성한 코드는 기능 완성보다 유지보수성과 검증 가능성을 우선해 리뷰한다.
